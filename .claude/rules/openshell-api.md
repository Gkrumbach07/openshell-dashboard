# OpenShell API Reference

**THE VENDORED GO SDK IS THE SOURCE OF TRUTH.** Since the SDK migration (PR #43), the BFF calls `github.com/NVIDIA/OpenShell/sdk/go` directly and this repo carries no local proto mirror or generated stub tree. Before writing any handler or TypeScript type, read the actual RPC/message definitions in `$(go env GOMODCACHE)/github.com/!n!v!i!d!i!a/!open!shell/sdk/go@<version>/openshell/v1/` (hand-written client wrappers with doc comments; `types/*.go` for message shapes) or via `go doc`. Never invent RPCs, fields, or lifecycle states. If a UI idea has no backing RPC, flag it — do not fabricate an endpoint. The SDK pin moves only together with the gateway the branch pins, to the commit of an upstream *release tag*, and the Follow upstream workflow makes that move on the `next` branch (hard facts 17 and 20). Never run `go get github.com/NVIDIA/OpenShell/sdk/go@latest`.

**Three narrow exceptions remain**, all in `backend/pkg/clients` and all on the SDK's generated proto client. `rawexec.go` does binary-safe file uploads, because the public `Exec().Run(...)` API takes no stdin and `Exec().Interactive(...)` always asks for a PTY (hard fact 22). `rawprovider.go` reads the keys of the credentials a provider holds, because the SDK's `ProviderFromProto` drops the map the gateway returns them in (hard fact 8); `rawprovider_allworkspaces.go` is the same read for the all-workspaces list. `rawprofile.go` reads and writes provider profiles, because the SDK's profile endpoint type keeps a host, a port and a protocol and drops everything else the gateway stores (hard fact 24). Do not add another unless the public SDK has a concrete gap you can point to, and delete each one when its gap closes.

## Services

| Service | SDK package | What we use |
|---------|-------------|-------------|
| `openshell.v1.OpenShell` | `openshell/v1` (`Client.Sandboxes()`, `.Workspaces()`, `.Providers()`, `.Policy()`, ...) | Sandbox (incl. stop/start), workspace, member, provider, profile, policy, draft policy, logs, SSH, services |

There is no `Inference` service: upstream has had no `inference.proto` since 0.1.0 and the SDK has no `Client.Inference()`. `inferenceCapable` and the inference category on a provider profile are profile data, not a service.

Skip `GatewayInterceptor`, `SupervisorMiddleware`, `ComputeDriver` — internal/operator only.

## Hard facts — do not violate these

1. **Sandbox stop/start exists (as of v0.0.113); no suspend/restart.** `StopSandbox` retains persistent state; `StartSandbox` resumes. `SandboxPhase` = UNSPECIFIED, PROVISIONING, READY, ERROR, DELETING, STOPPING, STOPPED, STARTING, COMPLETED, UNKNOWN. `COMPLETED` (proto value 9, in 0.1.0 and 0.1.2) is a sandbox whose main process exited with code 0; a non-zero exit is ERROR. Lifecycle: Create → Ready/Error/Completed → (Stop ⇄ Start) → Delete. There is still no suspend/restart RPC and no "Suspended" state — do not invent those.
2. **No workspace-scoped named-policy resource.** Policy exists as: (a) `SandboxSpec.policy`, then versioned revisions per sandbox. The gateway accepts a `CreateSandbox` without a policy (the CLI sends none unless `--policy` or `OPENSHELL_SANDBOX_POLICY` is set), but where it has no default to apply the sandbox's configuration is rejected and it never becomes ready (measured on 0.1.2 with the docker driver, 2026-10-06), so the dashboard keeps asking for one; (b) gateway-global via `UpdateConfig(global=true)`. No CreatePolicy/DeletePolicy/ListPolicies-by-workspace RPCs exist.
3. **Sandbox-scoped `UpdateConfig` may only change `network_policies` and inference fields.** filesystem/landlock/process are immutable after create — render read-only. Rule edits go to the gateway as `PolicyMergeOperation`s (`ConfigUpdate.MergeOperations`, what the CLI's `policy update` sends; `POST .../sandboxes/{name}/policy/merge`), never as a rewritten policy: the gateway's merge deduplicates endpoints and binaries and cannot overwrite a write that landed between a read and a save, and a whole-policy write did both. Replacing the whole network policy from a document is a separate, explicit action.
4. **No OCSF events API.** Observability = `GetSandboxLogs` (structured `fields` map on log lines) and `WatchSandbox` platform events. Never build an events query endpoint.
5. **No member-role-update RPC.** Role change = `RemoveWorkspaceMember` + `AddWorkspaceMember`.
6. **Sandbox operation identity is name + workspace scope.** User-facing sandbox operations — exec, logs, watch, SSH session creation — take the canonical sandbox *name* plus a typed `workspace_scope` (`datamodelv1.WorkspaceSelector`). Do not send `metadata.id` where the request message expects `sandbox`. This changed in the Sep 2026 SDK; the old `sandbox_id` field is gone.
7. **No Z3 verify RPC.** Prover verdicts appear only in `PolicyChunk.validation_result` on draft chunks.
8. **Provider model** (`datamodel.v1.Provider`): metadata, type (profile slug like "claude"/"gitlab"), credentials (map, `secret` option — strip before returning to browser), config (map), credential_expires_at_ms, profile_workspace. No endpoint-URL/status/model fields. Valid types come from `ListProviderProfiles`. Five things about it are easy to get wrong, all read from the gateway source at 0.1.0 and 0.1.2:
   - **Credential keys are env var names.** A provider's credentials are keyed by the profile credential's `env_vars` when it declares any, and by its `name` only when it declares none. Any other key is refused (`provider credentials are not declared by profile`), on create and on update. The profiles upstream publishes differ in the two (`openai`: `api_key` / `OPENAI_API_KEY`). The forms label a field with the name and send the value under the key (`credentialStorageKey` in `frontend/src/utils/providerCredentials.ts`). A credential that declares several env vars is accepted under any of them, and under more than one at once; the forms offer the choice and default to the first, or to the one the provider already holds, so that a new value replaces the old instead of adding a second copy. The refusal covers a profile that declares no credential: it takes no key at all, so there is no free-form "env var name / value" entry to offer (the TUI still has the fields for one; at v0.1.2 it shows them only after creating a provider of such a profile has failed, and what they send is refused).
   - **`profile_workspace` is the scope `type` is looked up in.** Empty is the platform scope: it resolves a built-in or platform profile, and a profile imported into a workspace does not exist there (`provider profile ... was not found in the requested scope`). The provider's own workspace resolves whatever profile that workspace sees: its own, else a platform one, else a built-in. No other value is accepted and it cannot change after create. A workspace profile may shadow a platform profile of the same id, and `ListProviderProfiles` then returns both, platform first, each with its `scope`. So the Add Provider form names the scope of the profile that was chosen — the workspace for a `workspace` profile, none otherwise (`profileWorkspaceFor` in `frontend/src/utils/providerProfiles.ts`) — which resolves that profile and no other, and leaves the gateway's own bookkeeping right: it blocks deleting a platform profile only for providers that name no scope. The OpenShell CLI and TUI send the provider's workspace by default and `--global-profile` sends none; both shapes work for a profile only one scope holds.
   - **Every read is redacted, and the SDK drops what is left.** The gateway returns `credentials` as `{KEY: "REDACTED"}`, folds the keys of `credential_handles` into it and clears the handles. The SDK's `ProviderFromProto` copies `credential_handles` and never `credentials`, so a provider read through the SDK names no credentials at all. `pkg/clients/rawprovider.go` reads the keys from the gateway's answer; only the keys are passed on.
   - **`UpdateProvider` merges.** A map that is absent changes nothing and a key with an empty value is removed. Send only what changes, as the TUI does, and do not build an update from a provider you read first: nothing upstream guards the literal `REDACTED`, so a redacted credentials map sent back would be stored as the credentials' new values. Reading through the SDK hides this only because the SDK drops that map. An expiry is a timestamp, and one that has passed is a credential that has expired, which the gateway withholds from every sandbox. The BFF refuses one at or before 1970 (a JSON `null` decodes to 0), and the form sends only a time still to come, so that a number typed in epoch seconds, which read as milliseconds is a day in January 1970, cannot switch a credential off. `clear_credential_expiration_keys` is how an expiry is removed; the BFF does not expose it yet. The same holds for `config`: an entry that is sent is written, so the Edit Provider form sends the entries changed since it opened and an empty value for each one removed, and nothing else (`configChanges` in `frontend/src/utils/providerForm.ts`). A form that sends every entry it holds puts back values that were changed elsewhere in the meantime. An update that names nothing is accepted and still writes the provider, moving its resource version on; the form does not send one.
   - **A provider can outlive its profile.** The gateway counts as the users of a profile only the providers whose `profile_workspace` is the scope the profile is deleted from, so a platform profile can be deleted from under a provider that names its own workspace, which is what the CLI and TUI send. The provider stays, with its type and its credentials; the TUI calls it legacy or unprofiled. `UpdateProvider` checks credentials against a profile only when one resolves, so such a provider takes a new value and an expiry for a key it holds. The pages say "unprofiled" only once the profiles have been read and none matches (`profileForProvider`), never while they are loading or could not be loaded.
9. **No list-images API.** Sandbox images are free-text OCI refs; community images by convention `ghcr.io/nvidia/openshell-community/sandboxes/<name>`.
10. **`GetGatewayInfo` returns only** status, gateway_version, compute_drivers[] and extensions[] (the non-secret outcome of the gateway's negotiation with each compute driver, credential driver, gateway interceptor and supervisor middleware). No uptime/db/TLS/auth-mode fields.
11. **Optimistic concurrency:** `AttachSandboxProvider`, `DetachSandboxProvider`, `UpdateConfig`, `UpdateProviderProfiles` accept `expected_resource_version` — pass the ObjectMeta.resource_version from the last read. `ApproveDraftChunk` similarly takes a `review_token` (from the chunk's last `GetDraft` read) pinning the exact evaluated candidate; the BFF falls back to resolving it server-side if the client doesn't send one.
12. **Workspace scoping:** most requests carry a workspace selector (`workspace_scope`); list RPCs offer `all_workspaces`. An empty workspace name does not mean "default": gateway 0.1.x refuses a named selector with no name (`workspace_authz.rs` at v0.1.2), so a route must never forward an empty path segment as a workspace. Workspaces themselves are top-level. Exactly four lists accept the all-workspaces scope — sandboxes, sandbox templates, providers and services (`ListOptions{AllWorkspaces: true}`, which makes the SDK ignore the workspace argument) — and the gateway answers it for platform admins only. `ListServices` refuses a sandbox filter in that scope. The BFF serves them at `GET /api/v1/{sandboxes,providers,templates,services}`.
14. **`List` is paginated; use `ListAll` unless you are paging deliberately.** Since the Sep 2026 SDK, `List(...)` takes no `ctx` and returns a `*Pager[T]`. The eager form is `ListAll(ctx, ...)` returning a slice, and it is what every BFF handler uses. `ListMembers` likewise has `ListAllMembers`, and since the 0.1.2 SDK a sandbox's `ListProviders` has `ListAllProviders`. `Policy().ListAll` takes `(ctx, workspace, sandboxName, opts...)` — pass `""` for both when listing global revisions.
15. **`Delete` returns `(*DeletionResult, error)`, and a nil error does not mean the resource is gone.** `DeletionOutcome` is one of Unspecified / Completed / Accepted / AlreadyAbsent. Only **Completed** and **AlreadyAbsent** establish completion; **Accepted** means the gateway queued asynchronous cleanup, and unrecognized numeric values must not be treated as completion. Convert through `models.FromSDKDeletion` rather than hardcoding `{"deleted": true}`.
16. **Network policy enum fields are proto enums, not free strings.** `access`, `enforcement` and `tls` on a policy network endpoint serialize through protojson as `NETWORK_ACCESS_PRESET_*`, `NETWORK_ENFORCEMENT_MODE_*`, `NETWORK_TLS_MODE_*`. The old lowercase spellings (`read-only`, `enforce`, `verify`) are no longer accepted by the gateway.

17. **Three links, each proven separately — and the gateway and the SDK move together, on `next` (ADR 0006 as amended by ADR 0009).** The chain is gateway → SDK → BFF → UI. *Wire* (gateway ↔ SDK) is proven only by running `backend/test/compat` against a real gateway; it is never inferred from version numbers. *Source* (SDK ↔ BFF) is proven by the compiler, `go vet` and the unit tests. BFF and UI ship together. Say which link failed: a compile error after an SDK move is a source migration, never "the gateway is incompatible". A branch pins ONE upstream release in `deploy/ci/gateway-pins.json` — the gateway and supervisor images and the SDK at that release's tag — and every change is tested against that gateway. Moving to another release is one commit that moves all of it: the pins file, `backend/go.mod`, `backend/go.sum`, the built-in release line when the minor changes, and the README's generated block. Nobody makes that commit by hand. `follow-upstream.yml` reads upstream's tags every hour and makes it on the `next` branch, as the first commit after `main`, titled `fix: move to OpenShell X.Y.Z`; `next` is the bump pull request opened early, and merging it moves `main` and cuts a patch release. Upstream pre-releases are tested ahead of the stable release in two ways: *check A*, the BFF as `main` builds it against the target gateway (a failure is the one issue labelled `compat-migrate`), and *check B*, CI on the `next` pull request, the console on the target's SDK against the target's gateway. A change that needs the upcoming release — an SDK method or an RPC the released gateway does not have — goes to `next`; everything else goes to `main`. An agent never moves the pins, never pushes to `next` and never opens its pull request: if a move is needed and the workflow has not made it, stop and say so. The compat suite proves only what it varies: a request field the gateway silently drops fails nothing (fact 18), so new compat tests should vary what the dashboard sends, starting with a non-default workspace.
18. **The wire link really breaks — loudly or silently — so what a build supports is measured, not assumed.** Between 0.0.116 and 0.1.0 upstream replaced `string workspace` on every request with a `WorkspaceSelector workspace_scope` message, in two steps. The SDK of 2026-09-10 (`90dbe545`) put the selector at *new* field numbers and reserved the old ones (`GetSandboxRequest` 2 → 3, `ListSandboxesRequest` 4 → 6, `CreateSandboxRequest` 5 → 8). Release 0.1.0 then moved it onto the *old* `workspace` numbers (`GetSandboxRequest` 2, `ListSandboxesRequest` 4, `ListProvidersRequest` 3; 7 on `CreateSandboxRequest`). Measured 2026-10-05: (a) `main` against 0.0.116 fails every workspace-scoped call with `workspace '\n\adefault' not found` — the gateway reads the serialized selector (`0A 07 "default"`) as the workspace *name*; `main` works with 0.1.0, 0.1.1, 0.1.2 and upstream HEAD. (b) Dashboard **v0.3.0** (SDK `90dbe545`) against 0.0.116 **fails silently**: protobuf drops the fields the gateway does not know, so the workspace is ignored — a sandbox created under `/workspaces/team-a` lands in `default`, every workspace page lists `default`, and nothing errors. Against 0.1.x and HEAD it fails with `workspace_scope is required`. v0.3.0 works correctly with no gateway. (c) Dashboard **v0.2.0** (SDK `387aea06`, 2026-09-02, still `string workspace`) works with 0.0.116, workspaces included, and fails with 0.1.2. So no build spans both sides, and gateway 0.0.116 is served by v0.2.0 (npm `0.2.0`, image `sha-701454a`) and a 0.2.x maintenance line cut from that tag — not by `main` and not by v0.3.0. Gateway 0.0.116 also has no sandbox-template RPCs (gRPC `UNIMPLEMENTED`). What exposes a silent drop is a field-by-field diff of the request messages between the gateway's proto tag and the SDK's proto (3 ignored fields for v0.2.0's SDK on 0.0.116, 70 for v0.3.0's, 0 for `main`'s on 0.1.0–0.1.2); it is not run automatically yet. What a build supports is one gateway minor release line, not a range of versions (ADR 0009). The line is the major.minor of the release `deploy/ci/gateway-pins.json` names (`node scripts/gateway-range.mjs` prints it), and that release is the one gateway the compat suite runs against for every change to the branch. As of 2026-10-09 `main` is for line `0.1`, built on and tested against 0.1.3: every gateway 0.1.x is `supported` — any patch, pre-release, dev build or downstream rebuild — and the BFF reports any other line as `unsupported`. The rest of the line is claimed because upstream promises no Stable break inside a minor, not because it was run here. Every compat run passes `-count=1`, because Go's test cache cannot see the gateway and replays a pass against one gateway as `ok (cached)` for another.
19. **The gateway's TOML config is versioned and the schemas are mutually exclusive.** Releases up to `0.0.116` need `version = 1`; `0.1.0` and newer need `version = 2`, which renames `compute_drivers` (array) to `compute_driver` (string), switches `image_pull_policy` to snake_case (`if_not_present`), and drops `sandbox_namespace`. A v1 config on a v2 gateway fails to start outright. `deploy/ci/gateway.e2e.v1.toml.tmpl` / `.v2.` hold both; select with `OPENSHELL_CONFIG_SCHEMA` (`auto` tries v2, then v1). `gateway-pins.json` names the schema of the pinned gateway (`config_schema`); a pin move carries it over, so a release that needs a new schema fails the compat suite until a person adds the template.
20. **A branch pins one upstream release — never `latest`, `dev` or `@latest`, and a pre-release only on `next`.** On ghcr.io the gateway tag `latest` is the newest *release* and `dev` is upstream HEAD; both move. Upstream tags a stable release `vX.Y.Z` and a pre-release `vX.Y.Z-pre.N`. Those two shapes are the only tags followed; anything else (`dev`, `vm-runtime`) is ignored. `deploy/ci/gateway-pins.json` holds `release` (without the `v`), that release's gateway and supervisor images pinned by digest (`tag@sha256:…`, the tag being the release), `sdk`, `sandbox_image` and `config_schema`. `main` and `release/**` pin a stable release. `next` pins the upcoming one, a pre-release until upstream cuts it, and `ci.yml`'s `pins a stable release` check refuses a pre-release in a pull request into any other branch. That check is deliberately not `compat`: it means "not released upstream yet", not "does not work". Never pin a `dev` build, with or without a digest: a dev gateway pulls `ghcr.io/nvidia/openshell/sandbox:dev` at runtime, so it drifts with upstream HEAD anyway — that broke `main` on 2026-10-02. The SDK module has no tags of its own, so the SDK pin is the pseudo-version of the commit the release tag points at (`v0.1.3` → `sdk/go@v0.0.0-20261009050449-e1f3c82caa3e`), written identically in `backend/go.mod` and in the `sdk` field; CI fails when they differ, when the pins file is malformed, or when it is not in canonical form (`python3 deploy/ci/upstream/follow.py format-pins` rewrites it). CI cannot tell a release tag's commit from any other commit; the Follow upstream workflow can, and its run summary says so when `main`'s SDK is not at the tag of the release it pins. One more thing restates the pins: the gateway release line compiled into the BFF (`BuiltInGatewayReleaseLine` in `backend/pkg/models/gateway_release_line.go`), so that an image knows its line with no build args and no environment. It must be the major.minor of the pinned release, and `node scripts/gateway-range.mjs --check` fails in CI when it is not; the pin move changes the constant when the minor changes. Upstream HEAD is no longer watched: pre-releases are, and a stable release is cut from one.

21. **Gateway settings are typed and type-checked.** `SettingValue` is a oneof of string, bool, int and bytes. Each registered key takes exactly one kind and the gateway refuses any other (`setting 'ocsf_json_enabled' expects bool value`). Gateways 0.1.0 to 0.1.2 register the same four keys: `ocsf_json_enabled` and `agent_policy_proposals_enabled` are bools, `ocsf_schema_version` and `proposal_approval_mode` are strings with a fixed set of values. `GetGatewayConfig` lists every registered key, and one that was never set comes back with an *empty* value: no kind. The API does not expose the registry (the CLI and TUI link it in), so the type of an unset setting cannot be read. The BFF mirrors all of this: a setting is a JSON string, boolean or integer in both directions, absent when unset, and nothing is coerced — the Settings page edits a value in the type it has and asks for the type when it has none.
22. **The gateway refuses any gRPC message over 1 MiB** (`MAX_GRPC_DECODE_SIZE` in upstream `multiplex.rs`, the same in 0.1.0, 0.1.2 and upstream HEAD on 2026-10-05). The unary `ExecSandbox` takes stdin as one field of one message, so a file near 1 MiB cannot be sent through it. `ExecSandboxInteractive` can: its first message is the same `ExecSandboxRequest`, and the gateway asks for a PTY only when that message sets `tty`, relays every later `stdin` frame as it arrives and closes the command's stdin when the request stream ends. The SDK's `Exec().Interactive(...)` hardcodes `tty = true`; the RPC does not. `pkg/clients/rawexec.go` uploads over it with `tty=false` in 256 KiB frames.
23. **Settings exist at two scopes and the global one wins.** `UpdateConfig` with a sandbox name and a `setting_key` sets a sandbox-scoped value (the CLI's `settings set <sandbox>`); with `global=true`, a gateway-wide one. `GetSandboxConfig` returns every registered key with its effective value and its scope (sandbox, global, or unset with no value), and `policy_source`: while a gateway-global policy is set, it and not the sandbox's own policy is what the sandbox enforces. While a key is set globally the gateway refuses a sandbox-scoped set or delete (FailedPrecondition, relayed as 409). `config_revision` and `provider_env_revision` are 64-bit fingerprints, not counters; they exceed 2^53 and travel as JSON strings. Measured on 0.1.2, 2026-10-06.
24. **A provider profile is replaced whole on update, and the SDK cannot carry one whole.** `UpdateProviderProfiles` stores exactly the profile it is sent, so a body that leaves a field out deletes it (measured on 0.1.2: a narrow body removed a profile's annotations and a credential's refresh settings). The SDK's `types.NetworkEndpoint` keeps the host, port and protocol of the 26 fields a profile endpoint has, so `pkg/clients/rawprofile.go` reads and writes profiles on the generated client and the DTO carries endpoints as protojson (`networkEndpoints`). Gateway 0.1.2 compiles in no built-in profiles: every profile is imported, at workspace scope or at platform scope (no workspace selector; `/api/v1/provider-profiles`).
25. **A draft chunk is approved only with its review token, in bulk too.** `ApproveAllDraftChunks` skips every chunk whose `review_token` is not supplied in `approvals[]` and still answers success, so an approve-all without tokens approves nothing. Read from gateway source at v0.1.2 (`grpc/policy.rs`); no chunk can be produced on demand to show it live.
26. **The gateway decides what a policy may say, and fills what is missing with defaults.** A host of `**` alone is refused (a recursive `**` is valid only as the entire first label of a longer host). An MCP endpoint sent without `mcp.versions` is stored with the gateway's default version list, so dropping that field on a round trip changes the policy without an error. Both measured on 0.1.2, 2026-10-06.
27. **Service endpoints: the name is optional and `domain` is not a choice.** A sandbox may have one unnamed endpoint (`service expose <sandbox> <port>`), removed with `DELETE .../sandboxes/{name}/services`. Gateways 0.1.0 and 0.1.2 store `domain: true` whatever the request says (read at both tags; confirmed live on 0.1.2).

13. **Secret fields** are annotated `[(openshell.options.v1.secret) = true]` in proto — grep for `secret` when adding a wrapper and never serialize those fields to the frontend.

## Auth per-RPC

User-facing RPCs require `Bearer` (OIDC JWT). `Health` is unauthenticated. Sandbox-only RPCs (ReportPolicyStatus, PushSandboxLogs, GetSandboxProviderEnvironment, SubmitPolicyAnalysis, ConnectSupervisor, RelayStream, GetInferenceBundle, IssueSandboxToken, RefreshSandboxToken) reject user principals — never wrap them.

## Streaming RPCs

`ExecSandboxInteractive` (bidi) — implemented via WebSocket relay in `pkg/handlers/terminal_handler.go`, and used without a TTY by `pkg/clients/rawexec.go` to stream file uploads (hard fact 22). The terminal runs `/bin/bash` unless the socket is opened with `?start=message` and its first frame chooses a command, working directory, environment or no login shell (the options of `openshell sandbox exec`); they travel in a frame, not in the URL, so environment values stay out of access logs. `ExecSandbox` (server-stream) — downloads are relayed from the SDK's `Exec().Stream` without buffering: a file as its bytes, a directory as a tar the sandbox writes (`tar cf - -C <path> .`, the CLI's own command). The SDK's `Files()` client cannot be used: its SSH transport reports itself unavailable. `WatchSandbox` (server-stream) and `ForwardTcp` (bidi) — deferred; use `GetSandboxLogs` + `GetSandbox` polling instead. The SDK's `Watch` yields sandbox snapshots only, so platform events and stream warnings are not reachable through it.
